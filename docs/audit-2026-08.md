- **Data:** 2026-08-23
- **Escopo:** todo o repositório — backend (Go), frontend (Next.js), infraestrutura/CI.
- **Método:** leitura direta do código-fonte, migrations, configuração de CI e imagens Docker já
  construídas nesta sessão; sem execução de ferramentas de profiling externas (sem browser real
  neste ambiente — os achados de acessibilidade/contraste abaixo vêm de cálculo de contraste
  WCAG sobre os valores reais de `globals.css`, não de inspeção visual).
- **Status:** todos os itens listados abaixo foram implementados no mesmo dia
  (commits `698eff4` backend, `71f9185` frontend). Uma imprecisão encontrada durante a
  implementação: `lib/api/client.ts` já tinha teste (`client.test.ts`) — o item "sem biblioteca

  mantido como o relatório original, sem reescrever o achado — este aviso é a correção.

## Resumo executivo

A base é sólida — resiliência (circuit breaker, outbox, idempotência), segurança (RSA próprio
para login local, bloqueio de conta, CSP com nonce, auditoria imutável) e CI (govulncheck, Trivy,
CodeQL, gitleaks) já estão em nível de produção madura, acima da média para um projeto deste
tamanho. As oportunidades mais valiosas não são bugs — são **padrões de arquitetura do frontend**
(busca de dados 100% client-side, sem RSC) e **lacunas de teste na camada HTTP do backend**. Duas
mudanças de alto impacto, poucas de baixo.

| Prioridade | Item | Categoria |
|---|---|---|
| 🔴 Alta | Buscar dados em Server Components em vez de `useEffect` client-side | Performance/Arquitetura |
| 🟡 Média | Testes de handler HTTP ausentes em 4 módulos do backend | Testes |
| 🟡 Média | Contraste insuficiente de texto de botão no tema escuro | Acessibilidade |
| 🟡 Média | Sem `loading.tsx`/`error.tsx` (convenção do App Router) | Boas práticas |
| 🟢 Baixa | Sem biblioteca de cache de dados (SWR/TanStack Query) | Performance |
| 🟢 Baixa | Sem link "pular para o conteúdo" | Acessibilidade |
| 🟢 Baixa | Sem `not-found.tsx`/`error.tsx` globais estilizados | Estética |
| 🟢 Baixa | Sem metadados OG/sitemap nas páginas públicas | SEO |

## Backend (Go)

### Pontos fortes confirmados

- **Arquitetura em camadas consistente** — `domain/application/infrastructure/transport` repetido
  em todo módulo, sem vazamento de regra de negócio para o transporte.
- **CI genuinamente rigoroso**: `gofmt -l`, `go vet`, `go build`, migrations aplicadas contra
  Postgres real, `go test` contra Postgres+RabbitMQ reais (não mocks), `govulncheck`, e as imagens
  finais escaneadas com Trivy (bloqueia HIGH/CRITICAL) — cobertura que a maioria dos projetos deste
  porte não tem.
- **Segurança em profundidade**: login local com chave RSA própria (independente do Keycloak),
  bloqueio de conta após tentativas, mitigação de canal lateral por temporização, CSP com nonce,
  RBAC, auditoria imutável, rate limiting distribuído via Postgres, chaves de idempotência,
  segredos via convenção `_FILE` uniforme em toda a configuração.
- **Resiliência**: circuit breaker nas chamadas externas, outbox transacional com validação de
  schema antes de publicar, DLQ com retry/backoff, desligamento gracioso.
- **Observabilidade**: métricas Prometheus, tracing OpenTelemetry, logs estruturados
  correlacionados por request id — cobertura de ponta a ponta, do proxy do frontend ao worker.
- **Falha rápida**: `config.Load()` recusa subir com configuração ausente/inválida em vez de
  falhar silenciosamente no primeiro request.
- **Imagens Docker enxutas**: `backend-api`/`backend-worker` compilam para ~44-46MB (binário
  estático Go + `ca-certificates`, usuário não-root) — praticamente o mínimo possível.

### Oportunidades

1. **🟡 Testes de handler HTTP ausentes** (`diario_oficial`, `integrations`, `secops`, `users` —
   os 4 módulos de negócio). Hoje só a camada `application` é testada (via repositórios/publishers
   falsos); nenhum teste exercita o `transport` diretamente — decodificação de request, mapeamento
   de erro para código HTTP, validação de payload. `internal/platform/localauth/transport_test.go`
   e `internal/platform/httpserver/middleware_test.go` (este último, escrito nesta sessão) já são
   o padrão a seguir: `httptest.NewRequest`/`httptest.NewRecorder` direto contra o handler, sem
   subir um servidor real. Prioridade média — não é uma lacuna de segurança (a lógica real está
   testada via application), mas é a única camada sem cobertura direta.
2. **🟢 Rate limiting é seletivo por desenho**: aplicado a login, emissão de ticket WebSocket e
   disparo de teste de integração — não aos endpoints de listagem (`GET /users`,
   `GET /integrations`). Provavelmente intencional (a spec original já escopava rate limiting
   assim), mas vale um registro explícito (ADR ou comentário) se a aplicação algum dia for exposta
   além de uma rede confiável — hoje um `GET /users` sem paginação abusiva não tem limite algum.
3. **🟢 Bloqueio de conta local é um valor fixo no código** (5 tentativas / 15 min — já documentado
   como trade-off deliberado no ADR 003). Só vira um problema se um ambiente real precisar de um
   valor diferente; hoje é YAGNI corretamente aplicado, não uma lacuna.

## Frontend (Next.js / TypeScript)

### Pontos fortes confirmados

- **CSP com nonce por requisição, sem `unsafe-inline`** — mantida em toda a superfície nova
  construída nesta sessão (tema, sidebar, notificações) sem um único atalho que a violasse; a
  troca de tema evita deliberadamente `next-themes` por causa disso.
- **Design tokens, não cores hard-coded** — `bg-primary`/`text-foreground`/etc. em vez de valores
  literais espalhados; provado duas vezes nesta sessão (troca de paleta inteira, depois um token
  novo só para o painel de marca) sem tocar em nenhum componente consumidor.
- **Autenticação dual bem abstraída** — Keycloak e login local convergem para o mesmo formato de
  `Identity`/sessão; nenhum componente downstream precisa saber qual caminho autenticou.
- **Disciplina de verificação ao vivo** — praticamente todo recurso construído nas últimas sessões
  foi validado com requisições HTTP reais contra os containers rodando, não só `npm run build`.

### Oportunidades

1. **🔴 Busca de dados 100% client-side** (a mudança de maior impacto disponível). Toda página
   autenticada é `"use client"` com `useEffect` + `useState<T|null>` + skeleton manual — o mesmo
   padrão duplicado em pelo menos 5 lugares (`dashboard`, `configuracao/integracoes`,
   `configuracao/integracoes/diario`, `configuracao/usuarios`, e o painel de feature flags).
   Consequências concretas:
   - Toda navegação paga uma cascata: HTML vazio → hidratação → `useEffect` dispara → fetch →
     re-render — o usuário vê o skeleton pelo tempo de um round-trip inteiro que um Server
     Component eliminaria buscando os dados antes de enviar o HTML.
   - Sem cache/dedup entre componentes: a lista de integrações é buscada de forma independente
     tanto pelo card de status em `/dashboard` quanto pela aba "Integrações" — a mesma
     informação, duas requisições nunca compartilhadas.
   - Cinco blocos de código quase idênticos (`load()`/skeleton/erro) em vez de um padrão único.

   O App Router do Next.js existe justamente para isto: qualquer página que só *mostra* dados no
   carregamento (não precisa reagir a estado do cliente) deveria buscar em um Server Component —
   reservando `"use client"` + `useEffect` só para o que é genuinamente interativo/ao vivo (o
   sino de notificações alimentado por WebSocket, o toggle de feature flag). Não é um retrabalho
   total: cada página vira um `async function Page()` que chama o backend diretamente
   server-side (via o mesmo padrão de sessão já usado em `app/(protected)/layout.tsx`) e passa os
   dados prontos para um componente de apresentação client-only só onde há interação de verdade.

2. **🟡 Sem convenção `loading.tsx`/`error.tsx`** — o mecanismo de Suspense boundary do App Router
   que substituiria os blocos manuais de skeleton/erro do ponto 1 por um padrão no nível de rota,
   automático assim que a busca migrar para o servidor.
3. **🟡 Contraste insuficiente no tema escuro**: calculado a partir dos valores reais de
   `globals.css` — `--primary-foreground` (branco) sobre `--primary` (`#a855f7`) no escuro dá
   **3.96:1**, abaixo do mínimo WCAG AA para texto normal (4.5:1); passa só para texto grande/
   elementos de UI (3:1). O texto de botões primários no tema escuro fica no limite da
   legibilidade. Correção possível: escurecer levemente `--primary` no modo escuro (ex.
   `#9333ea`) ou usar `text-foreground` em vez de branco puro nesses botões.
4. **🟡 Sem link "pular para o conteúdo"** — usuário de teclado/leitor de tela precisa tabular
   pela Sidebar inteira a cada carregamento de página pra chegar no conteúdo principal. Correção
   de uma linha, alto valor para quem depende disso.
5. **🟢 Sem biblioteca de cache de dados** (SWR/TanStack Query) — mesmo sem a migração completa
   para Server Components do ponto 1, adotar uma resolveria a duplicação de fetch entre
   componentes e adicionaria revalidação ao focar a aba, hoje inexistente (sair da página e
   voltar sempre mostra o skeleton de novo, sempre refaz a requisição do zero).
6. **🟢 Cobertura de teste concentrada no que foi construído mais recentemente** — 9 arquivos de
   teste no total; `Toggle`, `ThemeToggle`, `NotificationHistoryProvider` (construídos nesta
   sessão) têm testes, mas `IntegrationCard`, as páginas de usuários/integrações/configurações, a
   lógica de `Sidebar`/`Topbar`/`DashboardShell` e o próprio `apiClient` não têm nenhum.
7. **🟢 Sem `not-found.tsx`/`error.tsx` customizados** na raiz do app — uma URL digitada errado ou
   um erro de render não tratado cai na página padrão (não estilizada) do Next.js em vez de algo
   consistente com o resto da aplicação.
8. **🟢 Sem metadados Open Graph/Twitter, `sitemap.ts` nem `robots.ts`** — baixa prioridade para
   uma ferramenta interna, mas relevante se `/` e `/sobre` (páginas públicas) forem compartilhadas
   ou indexadas no futuro.
9. **🟢 Imagem Docker do frontend (~329MB)** é o tamanho esperado para um build standalone do
   Next.js sobre `node:22-alpine` (a base Node já é maior que a base Go usada no backend) — não é
   um problema por si só, mas vale rodar o bundle analyzer do Next.js quando o app crescer, para
   pegar cedo qualquer dependência server-only acidentalmente enviada ao bundle do cliente.

## Infraestrutura / CI

### Pontos fortes confirmados

Pipeline (`.github/workflows/`) mais completo que a média para este porte de projeto:
`gofmt`/`vet`/`build`/`test` (Postgres+RabbitMQ reais) + `govulncheck` no backend; `lint`/
`typecheck`/`test`/`build`/`npm audit` no frontend; build + escaneamento Trivy (HIGH/CRITICAL
bloqueante) das três imagens Docker finais; mais CodeQL, gitleaks e Dependabot rodando à parte.
Containers não-root, builds multi-stage, segredos via arquivo montado — tudo já no lugar.

### Oportunidades

1. **🟢 Job Docker do CI builda e escaneia, mas não publica** as imagens em nenhum registry — sem
   problema para o estágio atual (sem deploy automatizado ainda), mas vale conectar ao GHCR o
   quando esse próximo passo existir, pra não reconstruir a imagem no momento do deploy.
2. **🟢 `docker-compose.yml` base já é seguro por padrão** (sem portas de Postgres/RabbitMQ
   publicadas) — não há uma lacuna aqui, só uma observação: se o projeto for além de um único
   host, vale um exemplo de `environment:`/limites de recurso para orquestração real
   (Swarm/Kubernetes), que hoje não existe porque nunca foi necessário.
