## Resumo executivo

A base é sólida — resiliência (circuit breaker, outbox, idempotência), segurança (RSA próprio
para login local, bloqueio de conta, CSP com nonce, auditoria imutável) e CI (govulncheck, Trivy,
CodeQL, gitleaks) já estão em nível de produção madura, acima da média para um projeto deste
tamanho. As oportunidades mais valiosas não são bugs — são **padrões de arquitetura do frontend**
(busca de dados 100% client-side, sem RSC) e **lacunas de teste na camada HTTP do backend**. Duas
mudanças de alto impacto, poucas de baixo.

| Prioridade | Item | Categoria |
|---|---|---|
| 🔴 Alta | Buscar dados em Server Components em vez de `useEffect` client-side | Performance/Arquitetura |
| 🟡 Média | Testes de handler HTTP ausentes em 4 módulos do backend | Testes |
| 🟡 Média | Contraste insuficiente de texto de botão no tema escuro | Acessibilidade |
| 🟡 Média | Sem `loading.tsx`/`error.tsx` (convenção do App Router) | Boas práticas |
| 🟢 Baixa | Sem biblioteca de cache de dados (SWR/TanStack Query) | Performance |
| 🟢 Baixa | Sem link "pular para o conteúdo" | Acessibilidade |
| 🟢 Baixa | Sem `not-found.tsx`/`error.tsx` globais estilizados | Estética |
| 🟢 Baixa | Sem metadados OG/sitemap nas páginas públicas | SEO |

## Backend (Go)

### Pontos fortes confirmados

- **Arquitetura em camadas consistente** — `domain/application/infrastructure/transport` repetido
  em todo módulo, sem vazamento de regra de negócio para o transporte.
- **CI genuinamente rigoroso**: `gofmt -l`, `go vet`, `go build`, migrations aplicadas contra
  Postgres real, `go test` contra Postgres+RabbitMQ reais (não mocks), `govulncheck`, e as imagens
  finais escaneadas com Trivy (bloqueia HIGH/CRITICAL) — cobertura que a maioria dos projetos deste
  porte não tem.
- **Segurança em profundidade**: login local com chave RSA própria (independente do Keycloak),
  bloqueio de conta após tentativas, mitigação de canal lateral por temporização, CSP com nonce,
  RBAC, auditoria imutável, rate limiting distribuído via Postgres, chaves de idempotência,
  segredos via convenção `_FILE` uniforme em toda a configuração.
- **Resiliência**: circuit breaker nas chamadas externas, outbox transacional com validação de
  schema antes de publicar, DLQ com retry/backoff, desligamento gracioso.
- **Observabilidade**: métricas Prometheus, tracing OpenTelemetry, logs estruturados
  correlacionados por request id — cobertura de ponta a ponta, do proxy do frontend ao worker.
- **Falha rápida**: `config.Load()` recusa subir com configuração ausente/inválida em vez de
  falhar silenciosamente no primeiro request.
- **Imagens Docker enxutas**: `backend-api`/`backend-worker` compilam para ~44-46MB (binário
  estático Go + `ca-certificates`, usuário não-root) — praticamente o mínimo possível.

### Oportunidades

1. **🟡 Testes de handler HTTP ausentes** (`diario_oficial`, `integrations`, `secops`, `users` —
   os 4 módulos de negócio). Hoje só a camada `application` é testada (via repositórios/publishers
   falsos); nenhum teste exercita o `transport` diretamente — decodificação de request, mapeamento
   de erro para código HTTP, validação de payload. `internal/platform/localauth/transport_test.go`
   e `internal/platform/httpserver/middleware_test.go` (este último, escrito nesta sessão) já são
   o padrão a seguir: `httptest.NewRequest`/`httptest.NewRecorder` direto contra o handler, sem
   subir um servidor real. Prioridade média — não é uma lacuna de segurança (a lógica real está
   testada via application), mas é a única camada sem cobertura direta.
2. **🟢 Rate limiting é seletivo por desenho**: aplicado a login, emissão de ticket WebSocket e
   disparo de teste de integração — não aos endpoints de listagem (`GET /users`,
   `GET /integrations`). Provavelmente intencional (a spec original já escopava rate limiting
   assim), mas vale um registro explícito (ADR ou comentário) se a aplicação algum dia for exposta
   além de uma rede confiável — hoje um `GET /users` sem paginação abusiva não tem limite algum.
3. **🟢 Bloqueio de conta local é um valor fixo no código** (5 tentativas / 15 min — já documentado
   como trade-off deliberado no ADR 003). Só vira um problema se um ambiente real precisar de um
   valor diferente; hoje é YAGNI corretamente aplicado, não uma lacuna.

## Frontend (Next.js / TypeScript)

### Pontos fortes confirmados

- **CSP com nonce por requisição, sem `unsafe-inline`** — mantida em toda a superfície nova
  construída nesta sessão (tema, sidebar, notificações) sem um único atalho que a violasse; a
  troca de tema evita deliberadamente `next-themes` por causa disso.
- **Design tokens, não cores hard-coded** — `bg-primary`/`text-foreground`/etc. em vez de valores
  literais espalhados; provado duas vezes nesta sessão (troca de paleta inteira, depois um token
  novo só para o painel de marca) sem tocar em nenhum componente consumidor.
- **Autenticação dual bem abstraída** — Keycloak e login local convergem para o mesmo formato de
  `Identity`/sessão; nenhum componente downstream precisa saber qual caminho autenticou.
- **Disciplina de verificação ao vivo** — praticamente todo recurso construído nas últimas sessões
  foi validado com requisições HTTP reais contra os containers rodando, não só `npm run build`.

### Oportunidades

1. **🔴 Busca de dados 100% client-side** (a mudança de maior impacto disponível). Toda página
   autenticada é `"use client"` com `useEffect` + `useState<T|null>` + skeleton manual — o mesmo
   padrão duplicado em pelo menos 5 lugares (`dashboard`, `configuracao/integracoes`,
   `configuracao/integracoes/diario`, `configuracao/usuarios`, e o painel de feature flags).
   Consequências concretas:
   - Toda navegação paga uma cascata: HTML vazio → hidratação → `useEffect` dispara → fetch →
     re-render — o usuário vê o skeleton pelo tempo de um round-trip inteiro que um Server
     Component eliminaria buscando os dados antes de enviar o HTML.
   - Sem cache/dedup entre componentes: a lista de integrações é buscada de forma independente
     tanto pelo card de status em `/dashboard` quanto pela aba "Integrações" — a mesma
     informação, duas requisições nunca compartilhadas.
   - Cinco blocos de código quase idênticos (`load()`/skeleton/erro) em vez de um padrão único.

   O App Router do Next.js existe justamente para isto: qualquer página que só *mostra* dados no
   carregamento (não precisa reagir a estado do cliente) deveria buscar em um Server Component —
   reservando `"use client"` + `useEffect` só para o que é genuinamente interativo/ao vivo (o
   sino de notificações alimentado por WebSocket, o toggle de feature flag). Não é um retrabalho
   total: cada página vira um `async function Page()` que chama o backend diretamente
   server-side (via o mesmo padrão de sessão já usado em `app/(protected)/layout.tsx`) e passa os
   dados prontos para um componente de apresentação client-only só onde há interação de verdade.

2. **🟡 Sem convenção `loading.tsx`/`error.tsx`** — o mecanismo de Suspense boundary do App Router
   que substituiria os blocos manuais de skeleton/erro do ponto 1 por um padrão no nível de rota,
   automático assim que a busca migrar para o servidor.
3. **🟡 Contraste insuficiente no tema escuro**: calculado a partir dos valores reais de
   `globals.css` — `--primary-foreground` (branco) sobre `--primary` (`#a855f7`) no escuro dá
   **3.96:1**, abaixo do mínimo WCAG AA para texto normal (4.5:1); passa só para texto grande/
   elementos de UI (3:1). O texto de botões primários no tema escuro fica no limite da
   legibilidade. Correção possível: escurecer levemente `--primary` no modo escuro (ex.
   `#9333ea`) ou usar `text-foreground` em vez de branco puro nesses botões.
4. **🟡 Sem link "pular para o conteúdo"** — usuário de teclado/leitor de tela precisa tabular
   pela Sidebar inteira a cada carregamento de página pra chegar no conteúdo principal. Correção
   de uma linha, alto valor para quem depende disso.
5. **🟢 Sem biblioteca de cache de dados** (SWR/TanStack Query) — mesmo sem a migração completa
   para Server Components do ponto 1, adotar uma resolveria a duplicação de fetch entre
   componentes e adicionaria revalidação ao focar a aba, hoje inexistente (sair da página e
   voltar sempre mostra o skeleton de novo, sempre refaz a requisição do zero).
6. **🟢 Cobertura de teste concentrada no que foi construído mais recentemente** — 9 arquivos de
   teste no total; `Toggle`, `ThemeToggle`, `NotificationHistoryProvider` (construídos nesta
   sessão) têm testes, mas `IntegrationCard`, as páginas de usuários/integrações/configurações, a
   lógica de `Sidebar`/`Topbar`/`DashboardShell` e o próprio `apiClient` não têm nenhum.
7. **🟢 Sem `not-found.tsx`/`error.tsx` customizados** na raiz do app — uma URL digitada errado ou
   um erro de render não tratado cai na página padrão (não estilizada) do Next.js em vez de algo
   consistente com o resto da aplicação.
8. **🟢 Sem metadados Open Graph/Twitter, `sitemap.ts` nem `robots.ts`** — baixa prioridade para
   uma ferramenta interna, mas relevante se `/` e `/sobre` (páginas públicas) forem compartilhadas
   ou indexadas no futuro.
9. **🟢 Imagem Docker do frontend (~329MB)** é o tamanho esperado para um build standalone do
   Next.js sobre `node:22-alpine` (a base Node já é maior que a base Go usada no backend) — não é
   um problema por si só, mas vale rodar o bundle analyzer do Next.js quando o app crescer, para
   pegar cedo qualquer dependência server-only acidentalmente enviada ao bundle do cliente.

## Auditoria de AppSec — Keycloak/OIDC, gestão de segredos, controle de acesso (2026-08-26)

Pedida explicitamente pelo usuário no papel de "Engenheiro de Segurança de Software (AppSec) e
Code Reviewer Sênior", contra os 4 pilares: hardcoded values/gestão de `.env`, integração
Keycloak/OIDC, controle de acesso, sanitização/configuração. Método: leitura direta do código real
(não análise hipotética) — `internal/platform/auth/{oidc,claims,middleware}.go`,
`frontend/src/lib/auth/options.ts`, `app/api/auth/keycloak-logout-url/route.ts`,
`internal/platform/ws/ticket.go`, `internal/platform/httpserver/router.go` (CORS), varredura por
padrão de segredo commitado (`AKIA...`, `sk-...`, `ghp_...`, `BEGIN...PRIVATE KEY`) e por uso de
`localStorage`/`sessionStorage` no frontend.

**Resultado: nenhuma vulnerabilidade crítica, alta ou média.** JWT validado via JWKS real (não
decode — `go-oidc`, assinatura+`iss`+`aud`+expiração+algoritmo, sem `alg: none`), PKCE real no
client do frontend, token nunca em `localStorage`/exposto a Client Components (só num cookie
`HttpOnly` gerido pelo NextAuth), logout RP-Initiated real (front+back-channel), autorização
sempre decidida server-side a partir do JWT verificado (nunca de um campo que o cliente controla),
CORS sem wildcard, SQL sempre parametrizado, zero `dangerouslySetInnerHTML`, e uma defesa contra
timing attack em login local (`bcrypt.CompareHashAndPassword` num hash dummy mesmo quando o
usuário não existe) que vale destacar como prática acima da média, não só "sem problema".

Dois achados de **severidade BAIXA**, ambos com correção aplicada no mesmo dia:

1. **Credencial administrativa padrão documentada em texto claro** — `admin`/`Admin123!`, semeada
   pela migration `000011_local_auth.sql`, documentada no README com um aviso pra trocar antes de
   produção. Um aviso é disciplina humana, não um controle técnico: quem não lê o README (ou clona
   um ambiente sem revisar primeiro) fica com uma conta `nix-admin` de senha pública e conhecida,
   em QUALQUER ambiente que rode as migrations, dev ou não.
   - **Corrigido**: migration `000027_remove_default_admin_password.sql` remove a linha semeada
     — mas só SE a senha ainda for exatamente o hash do default documentado (nunca toca uma conta
     que o operador já trocou, identificada pelo hash divergente). Novo comando
     `backend/cmd/seedadmin` (`make seed-admin`) substitui a semeadura fixa: gera uma senha
     ALEATÓRIA (18 bytes de `crypto/rand`, nunca `math/rand`) a cada execução, mostrada uma única
     vez no terminal, nunca gravada em arquivo/log/migration; recusa sobrescrever uma conta já
     ligada ao Keycloak; reseta bloqueio de conta ao rodar de novo. `config.LoadDatabase()` (novo,
     `internal/platform/config`) deixa o comando standalone (só lê `DB_*`, não exige
     Keycloak/RabbitMQ configurados, mesmo raciocínio de `cmd/secscan`).
   - **Efeito colateral real, corrigido junto**: `frontend/e2e/auth.spec.ts` dependia do
     `admin`/`Admin123!` fixo pra logar — removê-lo sem mais quebraria o job `e2e` do CI. Corrigido
     lendo `E2E_ADMIN_USERNAME`/`E2E_ADMIN_PASSWORD` de variável de ambiente (com
     `test.skip(!password, ...)` — uma mensagem clara em vez de uma falha de login confusa quando
     não definida), e um novo passo no job `e2e` (`.github/workflows/ci.yml`) que gera uma senha
     com `openssl rand`, mascara com `::add-mask::`, e a propaga via `$GITHUB_ENV` — nunca a mesma
     entre execuções, nunca aparece em log.
2. **`KEYCLOAK_CLIENT_SECRET` carregada mas nunca lida por nenhum código** — já documentada como
   intencional no README ("reservada pra service-account/introspection futuro"), mas o
   `.env.example` não deixava isso claro, parecendo uma variável obrigatória. Corrigido: comentário
   no `.env.example` explicando que nenhum código hoje lê essa variável.

Verificado depois da correção: `gofmt`/`go build`/`go vet`/`staticcheck`/`deadcode` (mesmos 6 itens
intencionais de sempre) limpos; `go test ./...` inteiro passou (testes puros de

### Fechando o ciclo — Docker liberado, suíte inteira rodou pela primeira vez (2026-08-26)

Usuário configurou `sudo` sem senha pra Docker nesta sessão e pediu explicitamente pra "fechar o
ciclo": rodar a suíte inteira contra Postgres/RabbitMQ reais (não mais pular por falta de
`TEST_DATABASE_URL`) e reconstruir os containers da demo com tudo que foi feito. Os dois achados
abaixo só existiam porque nenhum dos dois cenários tinha sido exercitado de verdade até aqui —
exatamente a lacuna "escrito mas nunca rodado" repetida em quase todo commit anterior desta sessão.

1. **Migration `000027` falhava contra qualquer banco com histórico de verdade** — reproduzido
   rodando contra a demo ao vivo: a primeira versão fazia `DELETE FROM users`, que
   `audit_logs.user_id ON DELETE SET NULL` (migration 000005) transforma num `UPDATE` em cascata
   sobre `audit_logs` — recusado pelo gatilho de imutabilidade (migration 000008), revertendo a
   migration inteira. Nunca apareceu num banco de teste vazio (sem ninguém tendo logado como
   `admin` antes), só contra um banco com uso real. Corrigida trocando `DELETE` por `UPDATE`
   (`active=false` + `password_hash` sobrescrito com `crypt()` de bytes aleatórios via pgcrypto,
   confirmado bcrypt-compatível contra o pacote Go real antes de aplicar) — nunca toca
   `audit_logs`, preserva a linha e todo o histórico que aponta pra ela.
2. **4 testes de `diario_oficial` vazavam estado entre si** — `TestSyncAll_InactiveTerm_IsNotSynced`
   falhava de verdade (`Search called N times, want 0`): testes anteriores na mesma execução da
   suíte criavam `MonitoredTerm` ativo sem limpar depois, e `SyncAll` lista TODO termo ativo da
   tabela inteira. Corrigido com `t.Cleanup` em cada teste que cria um termo.

Depois das duas correções: `go test ./... -p 1` contra Postgres + RabbitMQ isolados (containers
descartáveis, `--rm`, nunca a demo ao vivo) — **100% verde, todos os pacotes, zero skip**, primeira
vez nesta sessão inteira. Migration reaplicada com sucesso contra a demo ao vivo depois da
correção (confirmado contra um banco com audit_logs real do admin, não só o cenário reproduzido);
`backend-api`/`backend-worker`/`frontend` reconstruídos e recriados (`docker compose build` +
`up -d --force-recreate`) — todos os 13 containers da demo `healthy` ao final, `postgres`/
`rabbitmq` recriados pelo próprio compose mas com os volumes nomeados intactos (dado confirmado
preservado: `goose_db_version` em 27, usuário `admin` presente, `audit_logs` com as mesmas 5
linhas de antes). `make seed-admin` rodado contra a demo pra repor um admin funcional depois da

### Job órfão preso em "processing" pra sempre (2026-08-26)

Usuário reportou, olhando `/seguranca`: um scan SonarQube preso em "0% Rodando" desde a noite
anterior, enquanto um scan disparado DEPOIS já tinha terminado — "tem como nos prevenirmos disso?".
Investigado contra a demo ao vivo: `jobs.id = 6ad5fbdf-...`, `status = processing`,
`started_at = 2026-08-26 00:19:02`, `attempts = 1` — nunca uma segunda tentativa, nunca um
`MarkFailed`/`MarkCompleted`. O worker que o processava morreu no meio do trabalho (o log do
container antigo não existe mais pra confirmar a causa exata — recreado antes desta investigação
começar —, mas o padrão é inconfundível: a mensagem do RabbitMQ que disparou o processamento já
tinha sido confirmada/ack MUITO antes do job "sumir", então nenhuma redelivery jamais chegaria).

**Achado estrutural, não um bug pontual**: não existia NENHUM mecanismo nesta plataforma pra
recuperar um job assim — nem no módulo `scanning`, nem em `diario_oficial`, nem na infraestrutura
compartilhada `internal/platform/jobs`. Pior: `JobsConfig.Timeout`/`JOB_TIMEOUT` existiam desde o
início do projeto, mas nunca foram lidos por nenhum código (confirmado via grep) — um teto de
tempo documentado que nunca teve efeito nenhum.

**Corrigido com o padrão padrão da indústria pra este problema** (o mesmo que Sidekiq/Celery/etc.
usam — um "stale job sweeper"): `internal/platform/jobs/sweeper.go` (`jobs.SweepStale`), registrado
como processor do worker (mesmo padrão de `ratelimit.Cleanup`/`idempotency.Cleanup`) — varre a cada
5min (primeira varredura imediata ao subir, recuperando órfãos deixados por um worker ANTERIOR)
todo job "processing" sem atividade há mais de `JOB_STALE_AFTER` (`JobsConfig.Timeout` renomeado
pra `StaleAfter` e finalmente WIRED — default 45min, escolhido acima do maior timeout interno de
qualquer scanner individual, `SCANNING_ZAP_SCAN_TIMEOUT` = 30min por padrão) e o dead-letra
reaproveitando o MESMO pipeline (evento de outbox, auditoria) que uma falha "normal" já tem —
`scanning.HandleScanDeadLetter`/`diario_oficial.HandleDeadLetter`, nunca um caminho novo — com um
motivo que deixa claro que foi órfão, nunca "max retries exceeded" (que nunca foi verdade pra este
caso: o job não passou por retry nenhum do RabbitMQ).

Aplicado contra a demo ao vivo depois de testado: `backend-worker` reconstruído e recriado, a
varredura rodou na inicialização e resolveu o job exato que o usuário reportou em menos de 10s —
`status` virou `dead_letter`, `error` com o motivo de staleness, `scanning.scan.failed` publicado
no outbox (confirmado `published_at` preenchido). A UI passa a mostrar "Falhou", não mais "Rodando"
pra sempre.

Verificado: `gofmt`/`go build`/`go vet`/`staticcheck`/`deadcode` limpos (mesmos 6 itens
intencionais de sempre); `go test ./...` inteiro (Postgres real, isolado) 100% verde, incluindo 4
testes novos de `sweeper_test.go` (varre job órfão de verdade, ignora job recente, tipo sem handler
registrado não derruba a varredura, erro de um handler não impede os demais no mesmo ciclo).

### Três achados reais direto do usuário: scans falhando, "Saúde das ferramentas" toda vermelha, progresso sem atualizar (2026-08-26)

Usuário pediu pra verificar os logs depois de rodar alguns scans: "iniciei alguns scans e
falharam", "a verificação se os serviços estão funcionais (Saúde das ferramentas) está aparecendo
tudo fora do ar", "senti falta de atualizar em tempo real o progresso". Os três eram reais,
diagnosticados direto contra a demo ao vivo (`docker logs`, consultas diretas ao Postgres, chamadas
à API com um token de verdade) — não simulados.

1. **`GET /scanning/scanners/health` reportava TODO scanner "sidecar URL not configured"** — mesmo
   com os 5 sidecars saudáveis e um scan real (Trivy/Gitleaks/Syft/Semgrep) tendo terminado com
   sucesso minutos antes. Causa: `docker-compose.yml`'s serviço `backend-worker` tinha a
   sobrescrita `SCANNING_*_SERVICE_URL` (endereços internos dos sidecars) desde uma correção
   anterior — mas `backend-api`, que é quem de fato serve `GET /scanning/scanners/health` (a tela
   de saúde é uma checagem SÍNCRONA sob demanda, não passa pelo worker), nunca ganhou a mesma
   sobrescrita: a feature "Saúde das ferramentas" (reestruturação de /seguranca) foi construída
   DEPOIS desse bloco `environment:` do backend-worker existir, e ninguém replicou o mesmo bloco pro
   backend-api na hora. Confirmado comparando `docker exec backend-api env` vs `docker exec
   backend-worker env` — as 5 variáveis vinham vazias só num dos dois containers. Corrigido
   replicando o mesmo bloco `environment:` (mesmos valores, comentário cruzando pra explicar a
   duplicação deliberada) no serviço `backend-api`. Depois da correção: os 6 scanners voltam
   `healthy: true`, confirmado contra a API real com um token válido.
2. **Scan SonarQube falhando com "context deadline exceeded" contra um repositório de tamanho
   real** — `infrastructure.SonarScanner`'s `scanRemote` (a chamada que pede pro sidecar rodar o
   `sonar-scanner` CLI) usava o MESMO `http.Client{Timeout: 30 * time.Second}` das chamadas rápidas
   (checagem de saúde, poll da Compute Engine, busca de achados) — mas o CLI faz análise LOCAL
   antes de subir o relatório, não é uma requisição HTTP simples, e pra um repositório real isso
   sozinho já passa dos 30s. Corrigido separando um `scanHTTPClient` próprio (10min) só pra essa
   chamada — as outras continuam com o timeout curto de 30s, cada requisição continua bounded por
   `ctx` independente do timeout do client (`NewRequestWithContext` em toda chamada). **Verificado
   de ponta a ponta contra a demo**: o MESMO alvo que falhava antes
   (`https://github.com/yurythx/papermoon`) rodou um scan SonarQube completo depois da correção —
   `status: completed`, `duration_ms: 66852` (bem acima dos 30s antigos), `findings_count: 666`.
3. **Progresso de scan "sem atualizar em tempo real"** — investigado a fundo antes de mexer em
   qualquer código (§ acostumado nesta sessão: reproduzir antes de corrigir). O log do backend
   mostrava `POST /api/v1/ws/ticket` devolvendo 401 a cada ~30s, indefinidamente, na mesma sessão —
   e também um `GET /ws status=504 duration=~9min`, que a princípio pareceu ser
   `chimiddleware.Timeout` (30s, aplicado globalmente) matando a conexão WebSocket no meio do scan.
   Investigação mais funda (lendo o código-fonte real de `go-chi/chi/v5/middleware.Timeout`, não
   assumindo) mostrou que essa teoria estava ERRADA: `Timeout` só cancela o CONTEXTO da requisição
   e tenta escrever 504 DEPOIS que o handler retorna — nunca fecha a conexão em si, e
   `ws.Client.readPump`/`writePump` nunca leem `r.Context()`, só os deadlines de leitura/escrita do
   próprio `gorilla/websocket`. O 504 registrado no log é só um artefato cosmético (a tentativa de
   escrita, sem efeito num ResponseWriter já hijacked, DEPOIS de `Start()` finalmente retornar —
   nunca a causa da desconexão). A causa real, confirmada pelo padrão de 401 repetindo pra sempre: a
   SESSÃO daquela aba do navegador tinha expirado (TTL de 1h do login local, sem refresh token —
   documentado no README) — e `NotificationClient.open()` não distinguia um 401 (sessão
   PERMANENTEMENTE inválida até um login novo) de um erro transitório de rede, então continuava
   reconectando com backoff PRA SEMPRE, sem nunca avisar o usuário que precisava logar de novo.
   Corrigido: `getTicket()` falhando com `ApiError.status === 401` agora vira um estado terminal
   novo (`"unauthorized"`, nunca agenda outra tentativa), mostrado na Topbar como "Sessão expirada —
   atualize a página" (vermelho, não âmbar — não é transitório). Qualquer OUTRO erro continua
   reconectando com backoff, comportamento inalterado.

Verificado: `gofmt`/`go build`/`go vet`/`staticcheck`/`deadcode` limpos (mesmos 6 itens
intencionais de sempre), `go test ./...` inteiro (Postgres isolado) 100% verde; frontend
`tsc`/`eslint --max-warnings=0`/`vitest run` (219 testes, +3 novos)/`next build` de produção,
todos limpos. Aplicado contra a demo ao vivo: `backend-api`/`backend-worker`/`frontend`
reconstruídos e recriados, todos os 13 containers `healthy`; achado 1 e 2 confirmados resolvidos
com chamadas reais à API (não só nos testes automatizados).
